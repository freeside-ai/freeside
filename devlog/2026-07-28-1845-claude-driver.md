# Production Claude Driver: Topology Gate, Credential Posture, and Export Binding

Work unit: #237 implementation slice (driver, `freesided submit`, production
`ExecutionExport` writer, real-run harness). This note carries the mandatory
trust-boundary record: the Early Claude Instruction-Topology Gate evidence and
adjudication, the credential-delivery posture decision, and the export/result
commit-ordering decision #318 will bind against.

## Early Claude Instruction-Topology Gate

Contract under test (issue #237; #375/#376 ward topology): the pinned
authenticated Claude CLI (2.1.220) must load the exact admitted host-vendor
instruction sentinel from the read-only native user-instruction mount
(`/root/.claude` containing exactly `CLAUDE.md`), complete real inference, and
perform required runtime-state behavior across startup, recovery, resume, and
child-process launch, with at most one writable mount (the leased auth-store
volume). A shell-only mount probe is not acceptance evidence.

Stop-the-lane criteria: every sentinel-passing variant needs writes under
`/root/.claude`; or a second writable mount; or relocated state breaks sentinel
loading; or only an env-token path authenticates and that violates the §5.4
mount posture. On stop: file the spine `kind:contract` topology issue, halt the
unit.

### Gate Verdict: Blocked On Credentials, Not On Topology

**The lane is not stopped, but the gate is not passed either.** The
stop-the-lane criteria are about the CLI needing writes beneath
`/root/.claude`; nothing observed says it does. What blocked the probes is
mundane and external: the operator's Keychain setup token is expired or
revoked, so no probe could complete a real inference, and every downstream
claim (exact sentinel loaded, startup/recovery/resume/child state behavior)
remains **unproven**.

This slice therefore ships the driver against the *designed* topology and
records the proof as outstanding. The implementation is arranged so the gate
can still stop it cheaply: the credential target, the argv, and the env are
three constants in `daemon/internal/exec/claude/spec.go`, and a gate outcome
that contradicts them changes those constants, not the driver's structure.
**No acceptance claim in this unit's PR rests on the unproven behavior**, and
#237 stays open (its acceptance slice runs after #318).

## Credential Delivery Posture

**Decision: the credential lives on the leased auth-store volume mounted at
`/var/lib/freeside/claude-auth`, and the CLI is pointed at it with
`CLAUDE_CONFIG_DIR`. No credential rides the agent environment or argv.**

Rejected alternative: passing `CLAUDE_CODE_OAUTH_TOKEN` in `AgentSpec.Env`.
It is the shortest path and the probes used it, but ward records the writer's
environment in the inspect report the conformance check compares, so the
token would land in an audit artifact and in the container's own process
environment, readable by anything the agent runs. §5.4's containment argument
is that the credential is a mounted store, not an ambient value.

The consequence is a real constraint on the topology: `/root/.claude` is the
ward's read-only instruction mount, whose proof requires that directory to
hold exactly `CLAUDE.md`, so the CLI's state directory cannot be its default.
`CLAUDE_CONFIG_DIR` relocation is what makes one writable mount sufficient.
**That relocation is precisely what the blocked probe (variant b) was meant
to prove**; it is the unit's largest unverified assumption, and the one to
check first when the token is restored.

## Evidence Before Export Before Result

The driver persists the released manifests, evidence blobs, and agent claims
before recording the `ExecutionExport`, then commits the Collect-visible
`StageResult`. This preserves both directions of the audit contract: every
observable completed head already has its export binding, and every export
binding already resolves to its evidence. A crash may leave unreferenced
content-addressed bytes, which an identical replay converges on; it can never
leave a durable row that asserts missing evidence. Rejected: recording the
export first, because a later evidence failure made the audit row false.

## Other Decisions This Slice Made

- **Production lane ownership is the dispatch intent's outbox row**, not a
  new attention item. A Run carries no workflow discriminator, so each lane
  needs a concrete marker; the outbox row already exists, is written in the
  same transaction as the run, and cannot be acquired retroactively by a
  foreign run. Rejected: a `run_proposal` marker item, which would surface an
  attention item for work the operator already approved at submit time.
- **Terminal outcomes are recorded, not raised as loop failures.** The
  walking skeleton fails the reconcile loop on a failed or lost invocation,
  which predates any failure-item vocabulary. Unattended operation cannot
  wedge the engine on one bad run, so the production lane records the
  terminal class in a durable inbox row and raises a deterministic
  `execution_failure` item.
- **Base is operator-pinned per daemon (`-base-sha`), not resolved per run.**
  Resolving a branch tip at admission would need a publish-lane transport
  capability that does not exist, and pinning the base on the Run would be a
  shared domain change. Only the workspace is derived per attempt, which it
  must be, since each handoff owns its volume. Recorded as a deliberate
  limitation: several sequential work items share one base until a run-pinned
  base contract exists.
- **Conformance is not run at daemon startup.** Unattended admission requires
  a durable, generation-current conformance record (#327, #320) that the
  store re-gates on every admission; a daemon that minted its own proof at
  startup would be attesting to itself. It stays an operator precondition, so
  a daemon started without one admits nothing.
- **The credential scan is a pattern scan, and says so.** ward requires a
  check-7 scanner and nothing implemented one. Its stated scope is material
  copied into the workspace, not material the agent encoded; its error names
  the file and pattern class but never the match, so a leak report is not a
  second copy of the credential.

## Refute-First Verification Pass

Two fresh-context lenses were run against the branch diff before push, each
prompted to disprove the unit's containment and durability claims (this unit
is a credential-leak surface and a returned-object trust boundary). Recorded
so confirmed findings are not re-raised and rejected ones are not re-argued.

**Confirmed and fixed:**

- **The daemon could not start in claude mode**: `ward.Config` was built
  without `ExporterCommand`, which the ward requires. Every claim about the
  production composition was therefore untested end to end. Now supplied from
  `export.HelperCommand()`, so the daemon and the image cannot drift on how
  the export is produced.
- **The credential scan was a silent false negative past 8 MiB**: it
  truncated each file and reported the remainder clean. The export's largest
  member is the agent's own transcript, which is both the most likely to
  exceed a cap and the most likely to echo auth material. Now streamed in
  overlapping chunks, whole file, bounded working set.
- **Export convergence could never converge**: `ExecutionExport` carries the
  evidence digest as a pointer, and the constructor and the store's decode
  each allocate their own, so `==` compared addresses. Every
  evidence-carrying replay would have been reported as a conflict, turning
  the exact crash window the convergence exists to close into a durable
  failure. Now compared by value, with a regression test.
- **The intent file was a decode boundary with no re-gate**: a tampered or
  corrupted record could retarget a recovered run's image, base, identity, or
  workspace. It now re-runs the containment gate on read, authenticates the
  full start against the durable admission, requires the exact derived seed
  path, and re-hashes the stored input and vendor-instruction bytes before
  reconstructing the prompt.
- **`-allowed-paths` defaulted to `**`**: declared-path scope is a §5.6/§5.8
  containment control, so unattended mode now refuses to start without
  explicit paths.
- **The importer was not bound to the admitted trust profile**: the production
  composition supplied only the operator allowlist, so repository-specific
  protected paths, commit-plan mode, and message rules were absent. Import now
  loads the exact profile digest from the authenticated admission and widens
  policy through `WithProtectedPaths`.
- **Submitted policy was opaque input**: arbitrary bytes were accepted,
  materialized, and then omitted from the agent prompt. Submit now strictly
  decodes resolved policy keys with per-key provenance, persists the
  `ResolvedPolicy` in the run transaction, stores the canonical keyed bytes,
  and includes those verified bytes in the rendered prompt.
- **Importer findings were ignored**: a non-empty finding set alongside a
  commit SHA could be surfaced as a completed candidate. Any finding now
  fails the stage before an export row is recorded.
- **Released export state was trusted twice**: both a fresh gate return and a
  decoded recovery record could supply an arbitrary cleanup path or fields
  inconsistent with the files on disk. The driver now requires the
  run-derived temporary-directory shape, a plain directory, the admitted
  observed base, and canonical manifest/evidence bytes before import or
  deletion.
- **Oversized admitted submissions wedged dispatch**: prompt rendering
  returned a start error after the outbox had dispatched, so every daemon
  restart retried and exited on the same work item. Unsupported rendered
  input now commits an authenticated failed result that the production lane
  surfaces as `execution_failure`.
- **Recovered exports repeated an already-closed ward recovery**: the first
  post-restart `RecoveryExported` return resumed import while the intent still
  said `running`, so another crash asked ward to recover its now-closed
  journal. Recovery now persists the same `exported` phase as a fresh handoff
  before import resumes.
- **Committed results were private-state assertions**: a valid-shaped edit to
  the intent could replace a completed head, evidence list, or status. A
  completed result is now accepted only when its phase-specific export
  payload hashes to the durable `ExecutionExport`, and non-completed/lost
  states are rejected when that row exists.
- **Export lookup errors were collapsed into absence**: transient store or
  admission re-gate failures permanently marked the run lost. The port now
  distinguishes confirmed absence from failure; failure leaves the exported
  intent retryable and fails startup closed.
- **Directory-free recovery dropped evidence identities**: when the export
  directory was gone, the fallback reconstructed only the head. It now
  authenticates the decoded evidence manifest against the durable row and
  restores the same ordered artifact digests as normal completion.
- **Production acceptance inherited the legacy missing-admission exception**:
  production dispatch requires an admission, but the shared completion gate
  treats an absent row as a pre-contract attempt and therefore accepted a
  completed production result after its audit authority disappeared.
  Production completion now requires that the row exists and passes the
  current reconstruction policy; the legacy exception remains scoped to the
  older conversation lane.
- Smaller: the started counter no longer drops a start whose dispatch mark
  failed; recovery interrupted by shutdown records canceled rather than
  failed; the loss branch re-reads the phase before overwriting it; two
  comments that described behavior the code does not have were corrected.

**Confirmed and deferred** (filed as #377, not fixed here): the gate's
auth-store mutation observation (`HandoffResult.AuthStore`, including whether
the writer mutated its store inside the window) is produced and discarded by
the driver rather than recorded.

**Could not be refuted:** the shell quoting (fuzzed against `/bin/sh` with
embedded quotes, escapes, newlines, and command substitution); the mount
topology (the built spec passes ward's own validation, and the credential
target neither overlaps the instruction mount nor adds a second writable
mount); the scanner never echoing a match; host instruction edits being
unable to retarget an in-flight run; submit's digest handling and identity
collision behavior; and the evidence-before-export-before-result ordering.

**Accepted by decision, stated as posture:** the CLI's session state shares
the leased credential volume, so one identity's run residue is visible to its
next run; and the rendered prompt rides argv into ward's durable journal, so
an operator secret placed in a specification or prompt package would be
persisted there. Both follow from the mount vocabulary being volume-only and
neither is a ward violation; recorded here rather than silently accepted.
