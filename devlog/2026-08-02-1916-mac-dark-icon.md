# Resolving the Mac Icon Appearance

Issue #465 reopened #444's unmet two-appearance acceptance. The owner chose
the contract-compliant path by assigning the issue for implementation rather
than ratifying the static treatment.

## Decisions

- **Chose an Icon Composer document over the static macOS asset catalog**
  because Xcode can compile one `.icon` package into system-selected default
  and dark renditions, while the earlier investigation proved that luminosity
  variants on `mac` asset-catalog slots are discarded. This supersedes the
  old full-bleed workaround: Icon Composer, not a hand-derived slot, now owns
  the platform mask, so the pending ratification recorded by #444 no longer
  governs the shipped icon.
- **Chose a palette-only dark treatment over redrawing the mark** because
  #465 is an appearance correction, not a new identity work unit. The dark
  raster preserves the accepted export's geometry and cutouts while using the
  visual register's umber `#16120E` ground and tawny `#C2912E` mark. The
  default raster remains byte-identical to #444's light export.
- **Rejected treating the two assets as interchangeable.** The light master
  uses an ink ground, vellum mark, and bronze detail; the dark rendition has a
  different two-color palette. Reusing the default raster would create an
  appearance entry without satisfying the visual contract.
- **Kept the adaptive catalog authoritative instead of shipping Xcode's
  standalone fallback.** Xcode 26.6 emits `AppIcon.icns` and
  `CFBundleIconFile` when `AppIcon` is designated through
  `ASSETCATALOG_COMPILER_APPICON_NAME`, even when standalone icon behavior is
  `none`. Finder prefers that static key over the appearance-aware catalog.
  The Mac target therefore compiles `AppIcon.icon` as a normal resource and
  names it with `CFBundleIconName` in its explicit `Info.plist`.

## Verification Findings

- The repository had no dark source asset before this unit: one static icon
  catalog compiled ten size entries, all without an appearance selector.
- An image-name specialization alone compiled but did not select the dark
  raster in Icon Composer's renderer. Two fixed layers with inverse opacity
  specializations render the intended asset in each appearance and make the
  selection visible in the source document.
- Dark Mode and dark icons are separate macOS 26 preferences. The installed
  boundary was exercised with **Icon & widget style** set to Default and to
  Dark (Always), while the interface remained dark; the original preference
  was restored after capture.
- The first installed build contained both appearance stacks but still showed
  the default artwork in Dark icon style. A unique-bundle-ID reproduction
  ruled out Launch Services caching, and removing `CFBundleIconFile` made
  Finder select the dark stack. The final package contains `Assets.car`,
  `CFBundleIconName = AppIcon`, and no `AppIcon.icns` or `CFBundleIconFile`.
- The installed bundle, not the source package alone, is the acceptance
  boundary. Verification therefore checks the compiled appearance renditions
  and captures Finder in both icon styles.

## Refute-First Findings

- **Confirmed and fixed:** the generated PNG initially carried a changing
  `tIME` chunk. The generator now excludes date and time chunks, and repeated
  runs produce the same SHA-256.
- **Confirmed and fixed:** the first decision-note heading used sentence case;
  it now follows the repository's title-case convention.
- **Rejected by verification:** the static fallback was not merely a stale
  bundle-ID cache. A uniquely identified copy still showed the default mark
  until `CFBundleIconFile` was removed.
- **Confirmed safe replacement:** the accepted 1024-pixel default master is
  byte-identical to the highest-resolution source removed with the old static
  catalog. Only its redundant size exports were deleted.

Revisit when: the signet artwork itself is redrawn or Icon Composer's fallback
rendering for the deployment target changes.
