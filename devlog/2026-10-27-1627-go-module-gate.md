# Go Modules Resolve From One Proxy

Plan revision 102. Mandatory note: a material plan change (§5.7) and
returned-object trust-boundary work, since the rebuild gate now reads
candidate-written `go.mod` and `go.sum` and decides whether a build may fetch
from the network. The contract is #2337, written in its planning session and
handed to implementation by the owner on 2026-10-27.

## Decision

Chose to pin the Go image build to one module proxy, `proxy.golang.org`,
with no `direct` fallback, and to treat that proxy's host as the authority
every Go module resolves from. The rebuild gate admits a `go.mod` or `go.sum`
change when `go.sum` holds the `/go.mod` hash of every module `go.mod`
requires (after module-path `replace`) and, when `go.sum` adds or changes a
module version or `go.mod` comes to require one its base did not, the
registry set declares `proxy.golang.org`. Unsupported or unreadable Go inputs
keep the `go_dependency_changed` refusal.

## Why

- **`go.sum` holds hashes, not sources.** Where a module comes from is the
  build's choice: Go's default `GOPROXY` is `https://proxy.golang.org,direct`,
  and `direct` clones a module the proxy doesn't serve from its own VCS host.
  "Every module resolves from a declared authority" is only true once the
  build names the source, so the build does. Rejected: reading the module
  path's host as its authority (it names the VCS origin `direct` clones from,
  not where a pinned build fetches); keeping `direct` (a module the proxy
  does not serve would bypass the declared set).
- **Nothing inherited can route around the proxy.** The warm step sets
  `GOENV=off` as well as clearing `GONOPROXY`, `GOPRIVATE`, `GOINSECURE`, and
  `GONOSUMDB`, and sets `GOSUMDB=sum.golang.org`. Go's `cfg.Getenv` falls back
  to the `go env` file when a variable is empty, so an empty variable alone
  would not override a base image's `go env -w` settings. This goes beyond
  the issue's list of cleared variables; the issue's own rationale for not
  checking zip hashes (Go checks the checksum database for what `go.sum`
  lacks) depends on it.
- **Only `/go.mod` hashes are required.** A real `go mod tidy` (testify plus
  x/text, five required modules) wrote a `/go.mod` line for every required
  module, but a tidy `go.sum` omits the zip hash of a module that provides no
  packages. Requiring zip hashes would refuse correct trees. Go verifies every
  download it makes against `go.sum` or the checksum database.
- **The reader recognizes only what Go writes.** `go.sum` lines must be a
  plain module path, a canonical version (optionally `/go.mod`), and an `h1:`
  hash; Go reads other hash kinds and then checks nothing against them, so
  such a line pins nothing, and Go drops a line holding the empty `go.mod`
  hash, so the gate does too. Lines split on whitespace as Go splits them,
  so CRLF and trailing spaces read as Go reads them. `go.mod` must use only
  the directives Go 1.26 reads, with plain paths and canonical semver
  versions in `require`, `exclude`, `replace`, and `retract` (Go resolves
  anything else as a query through the proxy), and no two `replace`
  directives for one module version with different targets. A false refusal
  costs what today's blanket refusal costs; a false admit sends an
  unreadable tree to the builder.
- **Clause tokens keep their names.** `go_dependency_changed` narrows to
  unsupported or unreadable Go inputs and `unpinned_source` gains a Go form,
  by doc comment only. Every record written under either value still fits
  its old meaning, so stored records and their readers stay correct and the
  unit stays `kind:feature`.
- **A proxy 404 or 410 is a repair.** With the proxy pinned, a module version
  it does not serve can only be fixed in the repository, so it classes as
  `ErrInstallFailed` with a `go.sum` checksum mismatch, whether go.mod, a
  replace, or a dependency's requirement chose the version. The match is
  anchored to the pinned proxy's URL; a checksum-database mismatch (no
  `go.sum` line named) and connection failures stay host faults. Fixtures
  are real `go mod download` output from Go 1.26.10.
- **Go's refusal of `go.mod` is a repair too.** The gate leaves some
  arguments to Go (a `godebug` key, a `tool` or `ignore` path), and modeling
  each would copy Go's parser. Go's "errors parsing go.mod" and "error
  loading go.mod" refusals class as `ErrInstallFailed` instead, unless an
  error line names a URL other than the proxy's 404 or 410: Go fetches while
  it reads a version it resolves as a query, so such a line is a fetch that
  failed. Without this, a candidate's unreadable `go.mod` would class as a
  host fault and upkeep would retry it.

## Refute Pass

A fresh-context reviewer tried to refute the change before the first commit
(`docs/agent-workflow.md` §refute-first), running real `go mod download`
against the live proxy.

- **Confirmed and fixed:** a `go.mod`-only switch to a version whose
  `/go.mod` hash `go.sum` already held skipped the authority clause; the
  gate admitted an `exclude` without a version and conflicting `replace`
  directives, which Go refuses; a 404 reached through a dependency's
  `requires` chain or a `replaced by` line was not classed as the
  candidate's; the version pattern admitted a prerelease identifier with a
  leading zero, which Go resolves as a query; the gate counted the empty
  `go.mod` hash as a pin that Go drops.
- **Allowed by decision:** after the pinned Go moves, a base whose `go.mod`
  names the old toolchain refuses every module change until a new image is
  admitted. This is the issue's rule 1 applied to the base; it is now
  tested.
- **Disproved:** no admitted input makes the warm step fetch from any host
  but the proxy (`GOENV=off` and the cleared variables hold, and `go.mod`
  sets none of them); the tokenizer matches Go or refuses on CRLF, a BOM,
  quoted strings, and block forms; npm verdicts are unchanged. The Go
  matchers also read npm build output, but npm prefixes its own lines, so
  only output the candidate's packages print could match, and that failure
  is the candidate's anyway.

## Revisit When

- A project needs a module `proxy.golang.org` doesn't serve (a private
  module): today it fails the build and classes as a repair no task can fix.
- The pinned Go is bumped: the install-failure matches are tied to its error
  text.
- Builder egress (#1793) or the adoption card (#2335) gains its own rule for
  declaring or proposing Go hosts.
