# Daemon Re-Runs and the Forced Drain

Work unit: #3105. Mandatory note: Tier A by path
(`internal/engine/production_workflow.go`). It builds on the update drain
from #3104 (`devlog/2026-11-11-2207-update-drain-hold.md`) and carries out
plan §5.2's "Re-run after a restart" and "Forced update" paragraphs
(revision 116), except for the crash-loop hold.

## Decision: Re-Run Like the Quota Park, in the Terminal's Transaction

Chose to allocate the next attempt inside the transaction that records the
lost or canceled terminal, after its milestone, over a separate sweep that
finds lost runs later. The quota park already proves this shape: the
terminal and its successor commit together, so no restart can leave a
terminal with neither a card nor an attempt, and a replay sees the
terminal already recorded and allocates nothing more. The rule grants
nothing: `reattemptProductionRunTx` allocates, and dispatch re-gates the
new attempt's admission against current policy like any other.

## Decision: Two Losses Per Chain, Counted From Lineage

Chose a limit of two losses per chain, read by walking `ParentRunID` while
the attempt reason is a daemon re-run reason, over a counter column. The
lineage already survives restarts and needs no migration, and any other
reason (an operator retry, a quota park) ends the walk, so a human's retry
starts a fresh chain. Two lets one unlucky restart and one more pass
silently; a third loss in a row points at something the operator should
see, so the card comes back.

Cancellations never count and don't break the chain. A graceful shutdown
or forced drain is routine during updates; counting it would exhaust the
limit for healthy work, which plan §5.9 rules out.

## Decision: A Loss the Starting Process Sees Keeps Its Card

The plan accepted that a loss found in the running process would also
re-run, assuming it arose only from an orphan after a failed live handoff.
Review found it is broader: ward closes any live handoff error that tears
down cleanly without a writer failure status as a loss, including a writer
that outlives its stop budget, a start refusal, and a provider-proxy
failure. Re-running those would hide a real failure for three times its
budget under a reason that blames a restart.

Chose to re-run a loss only when this process didn't start the invocation,
read from an in-memory set the engine fills on a successful `Start`, over
a durable cause on the loss, which would change the shared stage-driver
contract. The decision is still made once, in the terminal's transaction.
A restart re-dispatch gets `ErrDuplicateStart` and isn't marked. The one
gap: a process that dies after a live loss but before recording it hands
the next process an ordinary restart loss, which the limit bounds.

Revisit when the stage driver can report why an invocation was lost; a
durable cause would close that gap and replace the set.

## Decision: Only the Root Implementation Invocation Re-Runs

A fresh attempt starts from the run's base. For a remediation round or an
operator-feedback invocation that would discard reviewed work, so those
keep the card, as the quota park decides for the same reason.

## Decision: A Canceled Root Is the Daemon's When the Task Has No Stop

Chose to treat any canceled root implementation terminal as the daemon's
when the task has no cancellation and its workflow is open, over a new
cause field on the outcome. Every caller that cancels a root
implementation invocation was traced: a task stop records the task's
cancellation before it cancels (`CommitTaskStop`, the startup stop path);
`Driver.Close` and the forced drain request ward's durable cancellation
intent; the only other engine caller cancels specification invocations.

Revisit when a new canceler of root implementation invocations appears
that should end the run: it must record a task cancellation or close the
workflow first, or its runs will re-run.

## Decision: The Forced Drain Cancels Only Root Implementation Invocations

`freesided drain -force` cancels writers, the work that holds a drain
open longest and that a re-run can repeat from its base. Remediation
rounds, reviews, and verification run to their end, as under a plain
drain. An admitted attempt that hadn't started when the force ran has no
stage intent to cancel; it starts under #3104's rule that admitted work
runs, and a repeat `-force` cancels it.

One marker that doesn't decode, or a quarantined stage intent the daemon
can't reach, is reported after every other cancellation has run, so one
bad record never shields the rest; the force still fails loudly for it.

The forced row rides the existing `update_drain_request` seam, and
`update_drain_force` brackets only the cancellation, over a third seam for
the row: the row write is the same append the request makes.

## Decision: The Crash-Loop Hold Is Its Own Unit

Planning split the crash-loop hold out because it needs a durable start
log, a new table. Until it lands, a daemon that crashes in a loop re-runs
each chain twice before its card, which bounds the waste.

## Refute-First Findings

Each claim was tried against the code before commit, then by a
fresh-context reviewer.

- **A live failure could re-run as a restart loss.** Confirmed by the
  reviewer and fixed (the live-loss decision above), with a test that
  fails without the guard.
- **One bad record could make every forced drain fail before canceling
  anything.** Confirmed for an undecodable marker and fixed: the listing
  skips it and reports it last.

- **A re-run could start beside a live writer.** Disproved. A loss is
  recorded only after ward recovery proves the runtime gone and releases
  the lease (ward's `TestRecoverLeasedReleaseFailureKeepsRecordOpen` and
  `TestRecoverLeasedReleasesAfterCleanAudit`). A canceled result in the
  running phase is not committed by the pipeline
  (`commitResultLocked`); ward recovery turns it into `RecoveryCanceled`
  only from its durable cancellation intent, after teardown.
- **A shutdown could surface as a counted loss after a restart.**
  Disproved for shutdowns and forced drains that reach their
  cancellation: both write ward's cancellation intent first, so recovery
  reports canceled. Allowed by decision: a crash before the force's
  cancellation leaves writers to a plain restart, which records counted
  losses; the same-build drain stays in force across it.
- **A timeout or stall could cancel a root and re-run uncapped.**
  Disproved: no deadline wraps the pipeline's context, and the only
  `Driver.Cancel` callers are traced above.
- **The allocation could refuse inside the terminal transaction and wedge
  it.** Disproved: `productionAttemptParkable` answers the latest-attempt,
  closed-workflow, and stopped-task refusals first; the final-conclusion
  check reads the milestone written earlier in the same transaction.
- **A quarantined intent could re-run.** Disproved: quarantine records no
  terminal, and Inspect answers running for it (`exec/stage`
  quarantine tests), so the rule never sees it.
- **A definitive export rejection racing a shutdown records canceled and
  re-runs.** Allowed by decision: the stage driver already classifies any
  failure under a canceled context as canceled, the window is narrow, and
  the re-run passes every gate again.
- **A forced drain over an orphaned running intent turns a counted loss
  into an uncounted cancel.** Allowed by decision: the operator asked for
  the cancellation, and the outcome says what happened.
