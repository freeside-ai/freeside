# The Section 5.18 Capture Hooks (#443)

Work unit: issue #443, second link of Wave 3's serialized contract
track (after the §5.16 scheduler, #442/PR #450). Spec: plan §5.18
verbatim (the issue's Acceptance quotes it). This note records the
design decisions inside the spec's degrees of freedom and the
alternatives they rejected.

## Decisions

- **Capture rows are daemon-internal, never synced.** All five record
  shapes persist as internal rows (the 0024 rule: no
  `entity_version`/`as_of_revision`, writes reachable from `InternalTx`),
  because the issue pins "no `api/` change anticipated" and the 1B.2
  projection — not the raw records — is the client surface. Rejected:
  a synced aggregate like `schedules`, which would force an api/app
  contract rider this unit's declaration excludes. Unlike migration
  0024's milestones the capture rows *are* the authority the 1B.2
  frontier derives from, so they keep the full store reconstruction
  gate (decode → re-validate → cross-check extracted columns) rather
  than 0024's projection posture.
- **Declarations enter at submission, verbatim.** `freesided submit
  --work-unit <file>` carries the operator's explicit declarations
  (completion criterion, bound issue, dependency issue numbers,
  declared paths, contract serialization) into
  `ProductionRunSpec.WorkUnit`; they persist in the same transaction
  as the run, write-once (`putImmutable`). The daemon never parses PR
  or issue prose for any of them (§5.18's derivation rule; the
  merge-result audit set the precedent). A declared submission joins
  the declaration digest into the default run-id derivation, so
  changed declarations converge on a different run instead of
  colliding; undeclared submissions keep the existing derivation
  byte-for-byte.
- **One work unit per run, identity derived from the run.** The unit
  id is deterministic from the run id. Rejected: a standalone unit
  aggregate spanning runs — no current intake creates one, and §5.18's
  binding example is run-shaped. Revisit when remediation runs or the
  planner need many-runs-per-unit.
- **The PR binding is first-party, recorded on the ready path.** When
  production publication reaches its ready item, the daemon records
  the unit's PR binding from its own facts (admitted `BaseRevision`,
  published PR number, imported head SHA) — the "exact daemon-recorded
  work-unit binding". Both the fresh-publish and the converged
  ready-exists paths reach the same write-once record.
- **Merge and issue state are observed on the base-advance watch's
  cadence.** The §5.16 base-advance staleness watch is the only
  production site that periodically polls GitHub beside a live ready
  item, and a merge *is* a base advance, so the capture observation
  rides that handler: while the item is open it observes the bound PR
  (and, when the criterion needs it and the PR is merged, the bound
  issue), appends facts on material change, and records completion in
  the consuming transaction; when the item has concluded it takes one
  final observation before resolving the schedule, so an operator who
  merges and immediately dismisses the item is still captured. An
  observation failure on that final pass leaves the schedule armed
  (`observe_failed`) and retries at the next fire rather than
  concluding uncaptured. Rejected: a fifth `ScheduleKind` (widens the
  synced schedule contract and the api surface this unit excludes);
  a new engine ticker loop (regresses the §5.16 consolidation).
- **Completion is a pure domain evaluation over recorded facts.**
  `EvaluateWorkUnitCompletion(declaration, binding, pull fact, issue
  fact)` is the single trusted site for §5.18's exact rule: the
  observed pull must match every binding coordinate — repository id,
  PR number, admitted base ref, and recorded head — be merged, and,
  for the `bound_issue_closed_by_merged_pr` criterion, the bound
  issue must be closed by that exact merge commit (the issue `closed`
  event's `commit_id`). Partial (issue not closed by the merge),
  stacked or retargeted (merged base differs from the admitted base),
  unadmitted (a post-publication push, update-branch merge, or
  force-push moved the head past the recorded binding; Codex round 1's
  P1), and related (different PR, repository, or a manual/foreign
  issue closure) merges all evaluate false; the fixtures enumerate
  each. The visible trade of head exactness: a PR legitimately
  amended after publication (a human push, a later remediation round)
  completes nothing until a future contract revision lets the binding
  follow re-publication — fail-closed incompleteness renders as
  explicit staleness, a false completion would be silent.
- **The declared path scope derives from the resolved policy's paths
  key, never a second operator statement.** The submission already
  carries an explicit, gate-checked path allowlist (the runner's
  containment boundary), so the `--work-unit` file deliberately has no
  `declared_paths` field: a second statement of the same declaration
  could drift from what the runner enforces, and the capture record
  must be the scope the unit actually ran under. Dependency lists are
  canonicalized (sorted, deduplicated) at intake because their order
  carries no meaning and canonical form is what makes replay
  convergence byte-identical.
- **A declared submission joins the declaration digest into the
  default run-id derivation.** A changed declaration is a different
  work item, so it derives a different run id rather than colliding
  with the stored declaration as an immutable conflict; an undeclared
  submission keeps the pre-capture derivation byte-for-byte, so no
  existing run id changes.
- **The base-advance watch takes its own subject-liveness check.** The
  scheduler's built-in open-item check resolves a concluded item's
  watch before the handler fires — which is exactly the
  merged-then-immediately-dismissed case the final capture pass
  exists for. For this kind an existing item is live whatever its
  status: the handler resolves a concluded subject itself after
  capturing, and only a vanished item concludes without one. The
  visible trade: a permanently unobservable bound PR keeps the watch
  armed and retrying instead of resolving uncaptured (see Revisit
  when).
- **The closed-by link comes from the issue events API, not
  conjunction.** "Issue closed while PR merged" was rejected as the
  issue-criterion test: a manual closure beside a partial merge would
  satisfy it, which is exactly the inference §5.18 forbids. The issue
  `closed` event's `commit_id` equal to the PR's `merge_commit_sha` is
  the explicit link. A merged truth reads `merged_at` (present in both
  the single-PR and list responses) rather than the single-PR-only
  `merged` bool, so every read path agrees.

## Verification Findings

- `ReconcilePull` had no production caller and no merged fields; the
  publisher's identity convergence reads PR state only. Merge
  observation did not exist anywhere in the daemon before this unit
  (verified by sweep: no `merged`/`merge_commit_sha` reference outside
  janitor prose).
- `WriteTx` embeds `InternalTx`, so internal capture writes ride the
  scheduler's consuming transaction and the submission's Write
  transaction without new store surface.
- Refute-first pass (fresh-context reviewer over the full diff, per
  the finish line's returned-object-trust trigger), dispositions:
  - **Confirmed, fixed: the repository-identity check was vacuous.**
    The capture pass stamped the binding's own `RepositoryID` onto
    the observed facts, so the evaluator compared a value against
    itself and a name re-bound to a different repository (rename plus
    name reuse inside the installation) could mint a false
    completion. Fixed by decoding `base.repo.id` from the PR
    observation and stamping the observed identity onto both facts;
    the issue read is skipped entirely when the name does not reach
    the bound repository, and a response without the id fails the
    observation.
  - **Confirmed, fixed: an explicit empty `depends_on_issues` broke
    replay convergence** (`[]` vs `nil` after the omitempty store
    round-trip). Empty collections now normalize to nil in the
    constructor.
  - **Confirmed, fixed: the pagination off-host guard was
    prefix-confusable** (`api.github.com.evil.com` passed a bare
    prefix check); the separator is now part of the required prefix.
  - **Accepted by decision: permanent capture failure under a
    concluded item keeps the watch polling** (already this note's
    revisit condition; the reviewer's concrete permanent modes are
    folded into it below). Conditional requests keep the cost at
    304s, and occurrence records make the state visible.
  - **Rejected as already fixed:** the run-id digest over the
    pre-canonicalization declaration had been fixed in the pre-push
    self-review fold before the pass reported.
  - Angles probed with nothing real: spoofed/malformed forge fields
    (fail closed), duplicate/divergent completions, §5.16 handler
    semantics, migration/SQL shape.
- Codex rounds 1–2 (all four findings P1, all confirmed and fixed):
  - Round 1: the completion evaluator did not require the binding's
    recorded head, so a post-publication push merged code the daemon
    never admitted yet completed the unit. `PullMergeFact` now carries
    the observed head and the evaluator requires every binding
    coordinate; with the refute pass's repository-id fix this closes
    the class "a binding coordinate the evaluator does not require"
    by exhaustion (repository id, PR number, base ref, head).
  - Round 2a: the PR binding now records BEFORE the watches arm, and
    a declared-but-unbound unit is an observation failure that
    retries, never "nothing to record" — a crash between arming and
    binding could otherwise resolve a concluded item's watch with the
    merge forever unobserved.
  - Round 2b: whether a run is declared is fixed at intake — a
    declaration rides only the run-creating transaction, and
    declaring an existing undeclared run (explicit run id reuse) is
    refused, so an executing, published, terminal, or pre-capture run
    can never gain a retroactive unit.
  - Round 2c: the stored completion row is a done bit, and the
    store's promoted convention says a decoded trust bit is never
    trusted: `GetWorkUnitCompletion` now re-runs the trusted
    evaluator over the stored declaration, binding, and fact
    timelines (timelines, not latest state, so a post-merge issue
    reopen does not orphan a legitimate record) and fails closed on
    a row the evidence does not derive.
- Codex round 3 (one P1, two P2s, all fixed) — the third round on the
  stored-row trust class, so the fix widened the boundary once instead
  of adding another per-row patch. The posture it settled: within one
  store file, read re-gates guarantee internal consistency, never
  provenance (a writer who can forge one row can forge the rows any
  in-file anchor points at); provenance ends at the database file
  boundary (§5.2 permissions, §5.10 backup). What the capture pass
  adds on top is anchoring to the live records the handler already
  trusts and re-reads every fire.
  - P1: the reconstructed PR binding is now refused at the capture
    pass unless it restates the first-party anchors in hand — the
    armed watch's admitted repository and base ref, and the ready
    item's published head (`PRHeadSHA`) — before anything is observed
    or evaluated through it.
  - P2: the declaration read re-gate re-derives the declared scope
    from the run's stored resolved policy through one shared canonical
    definition (`domain.CanonicalDeclaredPaths`, also the intake
    derivation) and requires the run's project, so the scope the 1B.2
    projection reasons over can never drift from the boundary the
    runner enforced; `PutResolvedPolicy`'s digest binding to the run
    roots the chain.
  - P2: the issue leg re-verifies the repository name→identity
    binding after the issue read with a second conditional pull
    observation, so a name transferred and reused between the two
    requests fails the pass instead of stamping the earlier identity
    onto another repository's issue. Residual: a double rebind
    landing between the issue read and the re-check and back again
    within one pass; declined as requiring control of the original
    name's binding, at which point the repository itself is
    compromised.

## Revisit When

- Remediation runs, multi-run units, or the planner arrive: the
  one-unit-per-run identity and run-derived unit id stop holding.
- The §7 review stage (#427) binds observed check runs: the merge
  observation may move onto its richer PR polling.
- A merge lands after the base-advance watch expires or resolves: the
  1B.2 projection must render that gap as explicit staleness; if it
  proves common, capture needs an observation path with its own
  lifecycle.
- A bound PR becomes permanently unobservable under a concluded item
  (repository deleted, credentials revoked, a `bound_issue` that is
  actually a PR number, an issue history past the pagination bound, or
  an observation the fact vocabulary cannot express): the watch
  retries forever rather than resolving uncaptured; if that state
  ever occurs in practice, the capture pass needs a bounded terminal
  disposition that distinguishes permanent refusals from transient
  failures.
