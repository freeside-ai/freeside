# Recorded Facts in the Task Timeline

#1207 adds a computed task timeline, using the existing store records rather
than adding another event ledger. The timeline repeats the current task name
once with its `DisplayNameSource`; it does not invent naming history from the
current value. Name history belongs to #1321 and lifecycle facts to #1318.

Campaign allocation uses the initial specification run's submission instant.
Specification approval uses the initial implementation run's submission
instant: `engine.authenticateProductionAttempt` records approval in the same
store write that persists that run and its submission milestone. An attempt
retry inherits that approval, so it emits no second approval event.

Each read authenticates its runs and observations through the run timeline's
existing gates. Completion comes from the re-gated work-unit completion record,
not a milestone alone. A campaign with missing allocation evidence or a run
belonging to another task fails the projection. Empty tasks and legacy runs
without campaigns remain representable.
Membership is checked against both the task index and the validated run
enumeration. An index-only read could silently omit a durable run after an
inconsistent restore. Reusing `ListRuns` stays within the no-store-change
contract, at the cost of enumerating all run rows and failing on corruption
in an unrelated row. This matches the store's current local-daemon-scale
collection model; a narrower authenticated enumeration would need a separate
store interface change.
An approved initial attempt also requires its implementation in that validated
membership. Approval authentication can survive loss of both the run row and
its index edge, which otherwise hides approval history and leaves a dangling
supersession reference. Initial approval and implementation submission commit
together, so this absence is corruption. Unapproved initial attempts may have
only a specification run. Retry reservations commit before their runs, so
they do not establish the same presence requirement. Existing run reconstruction
already requires the specification and retry parent of a surviving run.
Once the root task is reconstructed, a propagated history row verdict is an
integrity failure. The original missing-row cause remains available for
diagnostics, but this endpoint gives the integrity classification precedence
over the generic 404 mapping. Otherwise a missing required campaign relation
would incorrectly report that the task itself was absent. Unknown root tasks
still return 404; infrastructure failures retain their original errors.

The refutation pass found that `GetWorkUnitPRBinding` alone checks shape and
column agreement but does not prove the run published that PR. The opened
event therefore also uses the existing published-resource authentication,
while retaining the original binding's recorded instant through later head
updates. The store-backed regression confirms that an internally consistent
wrong-PR binding is rejected even without a completion milestone. It also
confirms the valid crash window before the ready milestone remains readable.
Only a missing declaration or binding means there is no opened event. A corrupt
or unsupported recorded row fails the read; treating every row verdict as
absence hid contradictory PR history. The event remains limited to declared
work units, as #1207 specifies. `ReadyItemPRBinding` has a recorded instant,
but broadening the event to undeclared publication is outside that contract.

Automated review also found that discarding the task snapshot metadata could
serve a task from a future revision after an inconsistent restore. The task
now passes the same current-state snapshot gate as each run. A raw-database
regression changes only an empty task's revision and confirms it fails closed.
A later claim that zero task creation instants could pass reconstruction was
disproved: `GetTaskSnapshot` decodes through `Task.Validate`, which rejects
that value before timeline assembly.
Non-UTC creation instants do pass the task's existing validator, however.
The root event uses the same event validation as campaign and run events,
so every emitted task fact meets the UTC contract. A restored offset-bearing
creation timestamp is accepted by the task reader and rejected by the timeline.

Every list is newest first. Campaigns use allocation time, runs use submission
time, and equal instants use descending identifiers. A legacy group uses its
newest known submission; unknown instants sort last. This differs from the
existing run timeline's oldest-first milestone list, so #1209 must preserve
the task timeline's order when rendering it.

The existing mock run collection omits some specification predecessors.
Task fixtures group that collection without inventing the missing allocation
and approval events; the daemon golden pins the complete two-campaign history.
The mock computes each task read from current run observations. Review exposed
that a separate seeded task timeline could claim a new revision while omitting
a milestone just recorded through the mock's public mutation method.
Task reads also reuse the mock's existing task and run snapshot validators:
malformed seeded rows must fail reconstruction rather than return a successful
timeline that the daemon would reject. Regressions cover both input types.
Per-row validation does not establish membership across records. The mock also
checks that the selected runs exactly match the task's run and campaign sets
and belong to its project. Seeded missing, foreign, or unlisted runs and
inconsistent campaign or project membership must fail the read.
Raw timeline seeds are another input boundary. The mock checks the milestone
and hold shapes and parent bindings that it copies into task history, plus the
completion fact and its matching completion milestone. Review and invocation
details stay on the run resource; the fixture model cannot reconstruct the
daemon's publication authority. Swift dates represent instants without a time
zone, while the mock rejects the same unset creation and observation instants
as the daemon.

## Revisit When

The store records naming or lifecycle instants, or approval and implementation
submission cease to share one write. Extend the timeline from those recorded
facts rather than inferring them from current task state.
Revisit the whole-run enumeration when collection size calls for pagination
or a task-scoped store read is authorized.
