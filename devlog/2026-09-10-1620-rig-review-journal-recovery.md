# Recover Review Journals Under Stale Rig Ownership

An interrupted review can leave its volumes and network after the harness has
removed its containers. The stale rig then refuses release because those
resources remain, while ordinary journal recovery belongs to a daemon that
cannot start until the stale rig is released.

Use the existing review journal recovery inside the exclusive stale-rig and
database locks. The manifest restricts the candidate resource namespace; it
does not replace journal owner, fingerprint or lease validation. Keep the
existing manifest-authorized container cleanup first, then journal-authenticated
persistent cleanup, then the independent resource-absence gate. An independent
refutation identified that reversing this order strands an orphan workspace
while its seeder or observer remains attached.

Do not run the all-journal startup sweep. It can mark unrelated outcomes ready
without any runtime authorization call. Select only whole derived review
namespaces inside this manifest, and similarly restrict workspace-only recovery.
Preserve the existing lost-proxy outcome before teardown rather than closing
an interrupted intent without its failure evidence. No engine, provider or
publication loop runs here. Closed workspace provenance may remain for ordinary
startup reconciliation; it is not authority to recreate the removed volume.

Open the existing database without migration. Let a reviewed helper explicitly
select a newer recovery binary so old retained sessions can use the repair
without overwriting their saved executables or scripts. This choice does not
install a daemon or change the supervised-restoration contract.

Revisit when another journal owner needs this boundary. Do not generalize this
repair into deletion of all manifest-listed persistent resources by name.
