# Keep Task Identity Independent Of Intake And Runs

Issue: #1203. The owner-approved task vocabulary and lifecycle decisions are
recorded in #1206 and `2026-09-07-0921-task-vocabulary.md`.

Tasks use random opaque IDs. A separate project-scoped intake key deduplicates
source digests or repository/issue identities inside the same transaction that
creates the task. Run and campaign hashes keep their existing meaning. Task
membership records retain the order of earlier campaigns and runs.

The stored name starts with the identifier. The first approved specification
can replace that fallback or an agent suggestion. An operator name survives
approval, and later campaigns do not rename the task. The task-namer enum is
reserved here; its behavior belongs to #1208.

Legacy and demo runs can have no recoverable intake artifact. Their task source
is explicitly null, rather than a fabricated artifact reference. Migration
groups production attempts by project and original source digest and gives
other runs their own task. Label-intake history keeps its issue source, including
reservations committed before a proposal or specification dispatch exists. The
declaration, resolved policy, project, and occurrence-derived run ID establish
that source without trusting a stored admission's claimed subject. Corrupt
legacy bytes remain corrupt; assigning the indexed row a task never repairs
its authority-bearing body.

Independent refutation confirmed two binding defects during implementation:
a supplied task could bypass a campaign parent's task, and a raw legacy attempt
column could attach an orphan run to an unrelated intake key. Writes and reads
now verify campaign task continuity. Migration checks the run/attempt tuple
against the original dispatch or label declaration and occurrence. Regression
cases reject coherent run retargeting and the forged migration join while
preserving unstarted intake and ordered retry/campaign history. Operational
database errors abort migration instead of becoming orphan identities.

Task naming also changes attention presentation. The same transaction advances
affected attention snapshot versions, preserving decision bindings while making
out-of-order client reads reject the old name. Run projections carry the read
revision; task projections use it for both snapshot version fields.

A task ID adds no independent decision authority: it is fixed by the run ID,
identical to the subject ID for a task subject, or null on an unscoped subject.
The approval preimage therefore keeps the explicit original subject coordinates.
This preserves existing approval and recommendation commitments. The full
subject still participates in surface matching and store re-gating. Migration
authenticates the old surface before stamping both subject copies together;
unreadable or forged surfaces remain refused. We rejected widening approval
hashes with redundant metadata because it would invalidate sound commitments
without adding an authority check.

Fake-publication terminal commitments included the old subject encoding and
work-unit label. Migration authenticates those frozen encodings against the
original outbox task before rebinding the same publication facts. The current
commitment excludes the derived task reference and mutable display labels.
Malformed tasks, surfaces, and commitments stay unrepaired, including at the
pending-task crash seam. Approval and recommendation digests remain unchanged.
Both frozen terminal encodings matched 256 vectors produced by the base code;
the regression suite retains representative vectors with and without labels.

Task references also affect checkpoint restore. SQLite requires a transitional
default when adding a non-null column to populated runs, so insert/update
triggers reject missing or cross-project task references after backfill.
Restore copies tasks before runs while preserving the existing atomic restore
and foreign-key cleanup protocol.

Task lifecycle and current position are projections of the existing run
observations. They do not introduce lifecycle authority. Recorded completion,
abandonment, and WIP accounting remain #1318; the revised-specification trigger
remains #1083. Revisit the projection when those contracts land.
