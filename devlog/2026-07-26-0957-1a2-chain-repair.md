## Verification Findings

Material findings, each checked against code or forge state, not prose:

- `AuthIdentity` and `auth_store_mutation_lease` (§5.4), named in #237's
  deliverables, exist nowhere under `daemon/internal/` — the vocabulary
  #237 consumes was never landed.
- The admitted capability snapshot is in-memory only; #39's decision note
  explicitly deferred its persistence to "ward's real RunnerBackend
  selection", which is #237; no run/attempt record carries it.
- `exec.StartSpec` states its own widening contract for real drivers
  (`driver.go`): base/workspace identity, digests, credential/egress mode

  default; credential mounts are unconditionally read-only; a daemon
  restart mid-handoff has no adopt-or-rerun path.
- No caller of `publish.Transport.PushHead` exists outside its package:
  #298's fake publication supplies harness boundaries, so #288's gated
  composition is a prerequisite of real publication, not deferrable
  hardening.
- `images/` holds only `exporter/`; no pinned Claude base or gh-imgup
  project image.
- PR #298 records `Not run:` for the live publication; #232/#233/#234 are

## Decisions

- **One contract unit (#301), not several.** Admission persistence,
  `StartSpec` widening, handoff-result identity, and `AuthIdentity` are
  one durable-record vocabulary consumed together by #237. Rejected:
  splitting per concern — contract units are exclusive and serialized, so
  a split buys no parallelism and costs extra review rounds.
- **Two ward units (#302, #303), not four.** Paired by theme: writer-VM
  inputs (seeding, egress) and real-run mutation/recovery (lease,
  restart). Same declared paths serialize ward work regardless, so finer
  units add PR overhead without wall-clock gain; a unit that proves too
  large splits by ordinary deferral.
- **Keep #237's scope unchanged.** Rejected: widening #237 to absorb
  images or ward work — the same over-widening the 2026-07-24 chain
  amendment decomposed out of #236, and it would put lane territory
  inside a spine integration unit.
- **Backup waiver (owner decision, 2026-07-26).** The owner-only local
  checkpoint satisfies backup health, minus only its encryption-state
  dimension (the other doctor dimensions still gate admission), for the
  supervised 1A.2 runs; the
  §5.7 amendment in this PR records it as a mechanical admission gate
  (explicit operator-set `backup_encryption_waiver` naming the exact
  trusted numeric repository ID it covers, honestly reported per admission,
  rejected as invalid configuration by a build carrying the encrypted
  checkpoint), not a prose posture — review found "supervised"
  unenforceable, and a positional "first managed repository" unverifiable
  after re-onboarding or restore, as written. Encrypted
  `BackupCheckpoint` is #305, after #237 and before #238 (whose doctor
  packages the encryption check). Rejected: requiring it before #237 — it
  would add a serialized contract unit to the critical path to protect
  state that is recoverable and supervised during 1A.2.
- **#288 and #272 scheduled; six janitor/signet deferrals re-deferred**
  with dated comments (see #231's 2026-07-26 sweep record): none is
  exercised by the supervised single-writer, single-installation 1A.2
  posture.
- **Machine-state findings dropped from the plan.** The verification ran
  on a development machine; the operator machine is provisioned under
  #306, so local service/login state was recorded as moot, not as
  prerequisites.
