# Exit Runs Get A Project Skill

Eight exit runs (Wave 6, five under Wave 7, the #1211 rollout twice) have
each been driven from chat: the session derived the tracker's close
condition, ran `scripts/run-real-work.sh`, walked the operator through the
clients, filed findings, argued which ones block exit, and wrote the tracker
comment, with the shape reconstructed each time from the previous comment.
The shape has settled, and the same defects recur across runs (a PR merged
before the walkthrough, stale prompt packages, expired reviewer credentials,
stranded capacity), so the protocol is now a project skill:
`.claude/skills/exit-run/SKILL.md`, invoked as `/exit-run <tracker>
<target>`, with the tracker-comment templates and a digest of prior runs as
references.

## Decision

The skill runs the exit run; it does not generate a prompt for someone else
to run it. This is the opposite of the review-wave choice
(`devlog/2026-08-04-0823-review-wave-skill.md`) and follows the plan-wave
one (`devlog/2026-08-02-2007-plan-wave-skill.md`), for two reasons:

- **Independence is not the property at stake.** The wave review needs a
  reviewer with no author context, so its skill emits a prompt for another
  vendor's session. An exit run's evidence is the run's store, the forge
  records, and the operator's device reports; the session that drives the
  harness is the natural author of that record, and a second session would
  only re-derive it.
- **The variable part is operation, not derivation.** What changes per run
  is the tracker's close condition, the target, and the mode; the invariant
  part is preflight, the checkpoints where the operator acts, the evidence
  to record, the filing rules, the disposition test, and the comment shape.
  A prompt would restate the invariant part every time and go stale against
  the harness header.

Exit dispositions stay an owner decision. The skill proposes Required,
Investigate, Deferred, or Fixed in-run with a one-line reason each, and
records the owner's answer with its date. Every prior run worked this way
(the Wave 7 closure core, the #1211 19-finding follow-up, the run-70 "hold
only on Stop" call), and a session that decided exit on its own would turn
the tracker's close condition into whatever the run happened to show.

The disposition test is the tracker's stated outcome, not its checklist.
Wave 7's first run passed every exit-proof item while the operator could
not tell which card was live, and the owner adopted a closure core for it.
The skill states that rule so the next run applies it without relitigating
it.

## Rejected Alternatives

- **A prompt-generator skill**, matching review-wave: rejected above.
- **A shell script** wrapping the harness, the issue filing, and the
  comment: the harness already exists, and the judgment steps (what to
  file, what blocks exit, what the record claims) are the work. A script
  would either skip them or encode this run's answers.
- **Two skills, run and report:** the report depends on evidence only the
  running session holds (which actions ran, on which device, what the
  operator reported), and the split invites a run with no record.
- **Encoding the walkthrough and harness steps in the skill:** they live in
  `docs/production-walkthrough.md`, `docs/task-cancellation-check.md`, and
  the harness header, which change with the daemon. The skill points at them
  and states only where to stop and what to write down.

## Revisit When

- The harness gains a mode the skill's mode derivation doesn't name, or the
  walkthrough moves out of `docs/production-walkthrough.md`.
- A run's findings are dispositioned without an owner decision and nothing
  goes wrong; that would argue the proposal step is ceremony.
- The prior-runs digest stops being updated and the pitfalls list drifts
  from what actually recurs.
