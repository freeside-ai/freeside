# Cordoned Runs Are the Default Writer Class

Chose to run writers on the daemon's host as the owner's own processes, held
by a short list of fixed denials (the cordon), over keeping every writer in a
VM. A warded run holds a VM whose memory never returns to macOS. The owner
puts the 32 GB Mac Studio at about three warded writers;
`docs/spikes/ward-density.md` measured four as the useful ceiling, limited
by CPU before memory. The owner's hand-run sessions run six to ten agents at
once on the same machine. Freeside has to match that on the hardware it has.
Plan revision 134 adds the class to §5.7 and the matching rules to §§3.1,
5.4, 5.6, 10, 11, 14, and 15 (#3464, tracker #3462).

## The Owner's Decisions

From 2026-11-19 (#3464), unless noted:

- **Cordoned is the default for writer runs.** The implementer and
  remediator run on the host as the owner's account, sharing memory and CPU
  the way hand-run sessions do.
- **The cordon is a short deny list on an otherwise open machine,** plus the
  harness's own model review of each action. It is not deny-by-default.
- **Web: search and read anything, send nothing.** The owner will revisit
  this if it causes trouble.
- **Seeing its own work is standard:** a Simulator, the built app, a web
  preview. Full desktop control is a per-run grant, recorded as uncordoned.
  Revised for the Simulator on 2026-11-20; see below.
- **Warded runs stay for verification and for runs that warrant a hard
  wall:** material the owner doesn't trust, or a grant of something sensitive
  beyond the project. The split is by what a run handles, never by whether
  the owner is present.
- **Build order:** the secret-read rules and the ban on background services
  first, the network rule second.
- **The agent holds its own provider token.** No proxy substitution; the
  hold on `subscription_injected` (revision 103) stays.
- **Existing hardware only.** No second machine.

## Verification Is a Separate Revision

This revision doesn't move clean verification: it stays in the project
image's ward room and on the macOS verification executor's slots. The plan
says so without "never", because the owner has since decided to change it
(2026-11-20, recorded on #3464):

- A cordoned implementer's candidate will be verified cordoned, on the
  daemon's host as the owner under a verifier rule file, with the verdict
  recorded as cordoned.
- A warded candidate keeps a walled verifier and never goes to the cordoned
  one.
- Most slot work pauses; #3136 (a macOS VM per job) stays open.

The cordoned-verifier spike (#3526, PR #3542, unmerged when this note was
written) found that a cordoned verdict is not as trustworthy as a slot's:
Xcode's tools share the owner's temporary directory and Clang module cache
with every writer, which a writer was shown to write. The owner accepts that
residual for cordoned candidates, because the daemon, its verdict records,
and the App key already rest on the writer's rule file, and review, the
owner's approval, and the repository's own CI still stand between a verdict
and a merge. That change is a material plan change of its own, with its own
revision unit and note on tracker #3462, starting after this one.

## Earlier Decisions This Revises

- **Revisions 95 and 103 (§5.7, macOS Execution):** "a host-run writer
  context, on either Mac, waits for `subscription_injected` [...] they never
  fall back to copying the token." A cordoned writer now holds the
  identity's token under `subscription_contained` on the host. The hold on
  `subscription_injected` itself is unchanged.
- **Instance tiers (§10):** "Host-side runners are `ephemeral` only", under
  `attended_dev`. The cordoned class is a second exception beside the
  verification executor, admitted in `unattended` in every tier.
- **Operating modes (§5.7):** `unattended` admitted a host-side executor only
  as the credential-free verification class. The runner minimum is now per
  class.
- **What changed.** The UI-writer tier those rules pointed to needs a macOS
  VM, which the reference host can't hold two of, or a second Mac. Wards
  cap the host at three or four writers. The owner already
  carries the same exposure every day in hand-run sessions, and accepts it
  for this class in exchange for the parallelism, with the denials reducing
  it.

## Rejected

- **Hidden per-run accounts.** No login session, so no Simulator.
- **A separate logged-in agents account.** Setup friction, and a manual login
  after each restart.
- **One shared Linux VM.** Serves Linux work only.
- **A guest Mac for all agents.** A fixed block of memory, the problem the
  class exists to avoid.
- **A deny-by-default box.** Agents hit walls and the owner maintains the
  exceptions.
- **Proxy credential substitution.** The reason revision 103 holds
  `subscription_injected`: the provider would see the daemon's client
  sending Claude Code's requests.
- **Two accounts per run to keep the token from tools.** The owner's list
  gives no further reason. #3463 later showed that a token handed over on a
  file descriptor stays out of the tools' environment on one account, which
  is what the second account was for.

## Defaults Chosen at Planning

Each is the owner's to change in review; the rest of the revision stands if
one changes.

- **Credential mode: `subscription_contained`.** The mode says who holds the
  token, the isolation class says what holds the agent, and the two are
  always read together. Alternatives: `local_trusted`, which exists and is
  unused but means trusted inputs, the opposite of a writer's; or a new mode,
  a contract unit of its own for no difference in who holds the token.
- **Egress profiles: `host_open` then `host_web_read`.** The open first step
  gets its own profile so no cordoned run with the host's network is ever
  recorded as `provider_only`. The second step also gets its own, because
  its daemon-run page fetch reaches any site, which `provider_registry`'s
  risk class ("no attacker-operated host") excludes. The `host_` prefix keeps
  every cordoned egress record distinct from a warded run's.
- **A warded writer's web search stays open on #1659,** with the review
  launches. The owner's "search and read anything" was said of the cordon.
- **Hosts and tiers:** the daemon's host only, in every instance tier. An
  execution host would carry the owner's account exposure to a second machine
  and is out of scope ("existing hardware only").

## Evidence

- **`docs/spikes/cordoned-writer.md` (#3463).** The pinned CLI did a real
  writer task under a rule file that allows by default. It found the deny
  list needs the login keychain, writes to `~/Library/LaunchAgents`, and
  Freeside's own state (every daemon root, `~/.freeside`, and the volume
  images holding enrolled tokens) beyond the issue's first list; the token
  goes on a file descriptor, never in the environment; and a run's background
  children outlive the CLI. The owner's fallback, a first version with no
  fixed rules, isn't needed. Eight cordoned writers held normal memory
  pressure; the CLI costs about 125 MiB each.
- **The cordoned-verifier spike (#3526, PR #3542).** A writer under #3463's
  rule file alone can stop, restart, or attach to a process that runs as the
  owner, as the daemon does, and can write the verification executor's
  toolchain and caches. Added rules close each; that is denials 4 and 5. No
  rule hides one process's environment from another, so no process the
  daemon starts may carry a secret in its arguments or environment.

The rule file's text and path lists stay in the spike reports, and later in
the daemon's package docs, not in the plan.

## The Simulator Is a Per-Run Grant

The owner revised "seeing its own work is standard" for the Simulator only
(2026-11-20, in this unit's implementing session). Chose to deny the
Simulator by default and make it an operator's grant for one run, recorded
as uncordoned, over keeping it standard:

- **Code in a device runs as the owner with no rule file.** PR #3542 showed
  a process inside a device listing `~/.ssh` and `~/Library/Keychains`. The
  writer wrote the app the device launches, so with the Simulator standard
  any writer could step around the cordon whenever it chose, and the
  denials' proofs (#3470) would still pass.
- **No narrower allowance exists.** A broker that limits `simctl` verbs
  doesn't help, for the same reason. The cordoned-verifier spike closed it
  with one rule, a deny on the CoreSimulator services, and the macOS
  recipe's iOS build still passed under it.
- **The cost is small for Freeside's own app.** The screenshot suite renders
  phone layouts in-process, and the built Mac app launches as the writer's
  child under the rule file. A writer loses real iOS runtime behavior:
  navigation, the keyboard, safe areas.
- **The grant is narrower than desktop control.** A Simulator grant is its
  own kind beside #3478's desktop grant, so an iOS task doesn't get the
  owner's pointer and keyboard just to boot a device. #3473 becomes the
  grant unit.

Renders, the built Mac app, and a web preview stay standard. The
persistence capability became `supports_cordoned_launch_denial`, since the
denial now covers starting anything outside the cordon, not only through
launchd.

## Refute-First Review

One fresh-context reviewer read the revision's diff and tried to refute it.
Each finding's outcome:

- **Confirmed, fixed: secrets in the daemon's own children.** The plan said
  the daemon starts with no secret in its environment, but the daemon puts
  installation tokens in the environment of its git commands
  (`internal/publish/gitnet.go`, `internal/projectimage/source.go`) and the
  provider token in its one-shot model calls'
  (`internal/claudeinference/driver.go`). A cordoned tool can read any of
  them. The rule now covers every process the daemon starts, and the class
  isn't admitted until #3550 moves those secrets out.
- **Confirmed, fixed: a granted Simulator outlives the run.** Device
  processes aren't the run's children, so the end-of-run proof didn't cover
  them. The daemon now shuts down a granted run's devices before export
  (#3473).
- **Confirmed, fixed: "warded instead" had no decider.** It is now the
  operator's setting per project or task (#3471); admission never infers
  trust from a run's inputs.
- **Confirmed, fixed: a web preview needs a local service.** Step 2 refused
  every local service. It now refuses those outside the run; the run's own
  preview server is a requirement on #3466 and #3477, unmeasured so far.
- **Confirmed, fixed:** every instance root wherever it sits (proved by
  #3470); the writer count above; the macOS build of the pinned CLI version
  and its re-proof; the harness review claimed only as far as #3463's one
  probe; the ward-only residual sentence in §5.4; and Phase 4's referent.
- **Allowed, in the PR for the owner:** `subscription_contained` names a
  cordoned run only when read with its isolation class, a planning default
  above. How a granted, uncordoned run is admitted and exported is left to
  #3473 and #3478. Until a revision decides it, §10's `ephemeral`-only rule
  limits where such a run is admitted, not what it reaches, since an
  `ephemeral` instance shares the owner's account.

A second reviewer read the revised diff and reproduced two more gaps under
the spike rule files on the reference host:

- **Confirmed, fixed: the daemon's control socket.** It sits outside every
  daemon root and admits any caller with the daemon's uid
  (`cmd/freesided/pairing_control.go`), and it offers pairing codes, run
  settings, and task submission. A request from inside the cordon reached
  it. Denial 4 now covers every socket a daemon serves.
- **Confirmed, fixed: the owner's SSH agent.** Denial 1 refused reading
  `~/.ssh`, but `ssh-add -l` listed the loaded key, so with the network open
  a run could push to GitHub as the owner. Denial 1 now covers using a
  credential through a key agent.
- **Confirmed, fixed: another run can swap the worktree under the
  exporter.** The exporter runs outside the cordon and follows a link a
  concurrent run plants. Each run's rule file now denies other runs'
  worktrees, and the exporter never follows a link out (#3466, #3470).
- **Confirmed, fixed: programs the daemon runs with a secret** (git, the
  container CLI, the agent CLI) come from `PATH`, which the run can write.
  Denial 5 now covers them.
- **Confirmed, fixed:** `provider_only` is the default in a ward, not for
  every writer; the host's administrator policy file is named as open on
  #3466; and the `ephemeral`-only wording above.
- **Neither spike probed** the socket or the key agent. #3470's proofs have
  to cover both.

A third reviewer read the round-two fixes and found siblings:

- **Confirmed, fixed: the container runtime.** Its service runs as the
  owner, so a run could ask it to mount an enrollment's credential volume
  (the spike's own token helper does) or stop a live ward without reading a
  file or creating a launchd job. Denial 2 now denies the run that service;
  a cordoned writer runs no containers. Not run on the host.
- **Confirmed, fixed: programs the daemon runs without a secret.** The
  daemon also calls `tailscale`, `pgrep`, and fallback `git` by name, and
  once #3550 lands no child carries a secret, so the PATH rule now covers
  every program the daemon runs outside the cordon.
- **Confirmed, fixed:** the socket denial now excepts the run's own proxy
  and page-fetch endpoints under `host_web_read`; cordoned worktrees live
  under one directory so a rule written at launch covers later runs; and
  §14 says writes, not reads, to other runs' worktrees are denied.

## Revisit When

- The web rule ("send nothing") causes trouble in real runs.
- #3475 measures the real number of concurrent writers the host carries.
- A revision lifts the hold on `subscription_injected`.
- The follow-up revision on tracker #3462 moves a cordoned candidate's
  verification onto the host, or the verification executor's inputs become
  unwritable by the owner's account.
