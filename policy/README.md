# policy

Per-project policy configuration: initiators, review policy, gates, budgets, security mode, telemetry (see `docs/plan.md` §5.12). The Phase 1 workflow is a Go state machine in `daemon/`; YAML here is policy only, never a pipeline DSL (a DSL waits for three genuinely different workflow shapes).

This directory is **control-plane** content: the daemon loads it only from an approved default-branch commit, running stages snapshot its digests, and workspace copies are data (see `docs/plan.md` §5.8). It holds the policy for work *on Freeside itself*, which becomes a managed repo only as the bootstrap test after the deliberately boring first repository proves the path (plan §11); a consumed repo's policy lives in that repo.

- **Toolchain:** YAML (policy values interpreted by the daemon's code-defined state machines).
- **Scope boundary:** policy configuration only. Changes here are control-plane changes: gated, reviewed like code, never batched silently into feature PRs.
- **Status:** layout and file formats fixed (below); no files until an operator commits the baseline patch `freesided auth adopt` prints.

## Agents, Fragments, and Lineups

The admitted-agent tree (`docs/plan.md` §5.4, revision 39; the contract types live in `daemon/internal/domain`). Every document here is operator-authored configuration, reviewed as a diff; the daemon never writes this tree. Enrollments, generations, and admissions are facts and live in the daemon's store, never here.

Reserved layout:

```text
policy/
  agents/
    <agent-name>            # one four-line agent document (who/through/running/asking)
  fragments/
    routes/<route-name>     # service operator, protocol, authorities, billing, terms basis
    adapters/<adapter-name> # Freeside adapter build, pinned harness build, capabilities
    offers/<route-name>/<offer-name>  # one route's offer of one model
  lineup                    # the deployment lineup: one line per role naming a selection and a prompt
  agents.lock               # the name-to-digest map for the tree revision
```

Binding rules, fixed by the contract:

- **Names are tree-level.** The name-to-digest map (`agents.lock`) binds each name to the digest of its canonical body; no name enters any digest, so a rename changes nothing and a content edit changes exactly the digests that consumed it.
- **An offer lives under its route.** Which route an offer is authored under is a tree fact (the directory), supplied to resolution as context, deliberately outside the offer's digest.
- **The lineup names a selection.** A line maps one role to a selection and a prompt, and resolves to one key in the resolved policy: `lineup.role.<role>`, with the value `<enrollment-id>/<model-id>/<effort>/<prompt-name>@<prompt-digest>`. The enrollment id is the one adoption mints (`<identity>/<client>`), the model id is the one the enrollment's harness reports, and the effort is the harness's own string (Codex has no `max`; its top effort is `xhigh`). One key per line means a project lineup overrides a whole line, never half of one. The prompt is named by digest, so a line never follows a prompt edit nobody approved for the role.
- **A line resolves at admission, not at tree load.** Admission joins the line's enrollment and identity as the store holds them, the adapter the role's launch shape picks for the enrollment's client and the line's effort, and the enrollment's discovered model catalog. A line whose model the harness no longer reports, or whose effort that model does not offer, fails that role's admission by name and raises the ordinary card; the tree still loads. The agent documents and offers stay in the tree for the client's name translation, the routing policy, and the alternate-agent record, and admission reads none of them.
- **Lineup keys are role names.** `<role>` is a name from the closed role list (`docs/plan.md` §5.13; `RoleName` in `daemon/internal/domain`): `specifier`, `implementer`, `remediator`, `reviewer`, `shadow_reviewer`, `diagnostic`, `task_namer`, `publication_author`, `finding_classifier`, `finding_adjudicator`, `drift_auditor`, `attention_discussion`, and `briefer`. A stage name is not a role name, and `verification` is an engine job, never a role; both are rejected, like any unknown role. A role needs a line only while policy asks for its work, and one role never borrows another role's line.
- **Judgment roles have baseline lines.** `freesided auth adopt -judgment-model <id> -judgment-effort <effort>` writes a line for every judgment role with a built site (`diagnostic`, `task_namer`, `finding_classifier`, `finding_adjudicator`, `drift_auditor`, `attention_discussion`, and, when adopt is given `-judgment-publication-author-prompt`, `publication_author`), each selecting `<id>` at `<effort>` on the implementation identity's Claude enrollment. Without `-judgment-model` adoption writes no judgment line. Give the exact model id the Claude CLI reports, because adoption does not check it. Adoption also writes the call agent `claude-code-call-default` on the offer `claude-code-call-default` for the client's name translation; admission does not read them. A judgment call runs through the one call adapter that sends the line's effort, `claude_code_call_v2` for the efforts adoption writes, pinned to the Claude CLI build the call launch was audited on, because a judgment call is admitted only under an audit that names its adapter's build. Each line names the role's prompt: a code-owned versioned name for every role but the publication author, whose prompt is the operator's file by content digest. A deployment adopted before these lines existed, or before the call offer, adds them by patch: run `freesided auth adopt -judgment-model <id>` again for the baseline, take the call agent, its offer, its adapter fragment, the lineup lines, and the lock entries from the patch it prints, and commit them (`daemon/README.md`, Select Agents Through The Lineup, has the steps). Until a role's line exists its sites return their fail-safe and the daemon raises a `system_health` item naming the role (`daemon/README.md`). A judgment call authenticates with the stored credential of the enrollment its line names, so a line moved to another enrollment is billed to that enrollment's account.
- **A judgment role takes its model and effort from its line.** To give a role its own, edit the model and effort in its line and commit. Give the exact model id the Claude CLI reports: an alias or a short name does not work, because the call compares the id the completion reports with the id it passed, so every call on that line fails. The call then launches with `--model <model-id>` and, for an effort other than `harness_default`, `--effort`. The earlier adapter `claude_code_call_v1` sends `harness_default` only. Both adapters send `harness_default`, so while a tree holds both, a line at `harness_default` has no one adapter: the role is unbound and its sites return their fail-safe until the line names another effort. A deployment adopted on it takes the v2 fragment and its lock entry from the patch a fresh `freesided auth adopt` prints. A judgment line on the model `claude-code-native-default` is refused: it names no model and no daemon flag supplies one, so the role is unbound, its sites return their fail-safe, and preflight fails (`daemon/README.md`). A ward role on that model still launches, with no `--model`, but adoption no longer writes one there.
- **A review role takes its model and effort from its line.** `freesided auth adopt` writes both review agents: `codex-review-default` for `reviewer`, on the adapter `codex_review_v2` and an offer whose `route_model_id` is `-review-model`, asking `-review-effort`; and, with the shadow arm on, `claude-shadow-review-default` for `shadow_reviewer`, on the Claude ward adapter and its own offer for `-shadow-review-model`, asking `-shadow-review-effort`. Each review line selects that model and effort on the review identity's enrollment. To give a review role another model or effort, edit them in the role's line. The review launch always passes a model and an effort, so the daemon refuses a review line on `claude-code-native-default` or at `harness_default`, and preflight fails. The adoption flags take a Freeside level and the line holds the harness's string; Codex has no `max`, so `-review-effort max` writes `xhigh`. A changed model or effort is a different review configuration digest, which needs its own approval. `codex_review_v1` sends `harness_default` only, so a reviewer left on it is refused; take the v2 fragment and its lock entry from the patch a fresh `freesided auth adopt` prints (`daemon/README.md`, Select Agents Through The Lineup, has the steps).
- **The reviewer line picks the review harness.** A line on a `codex_cli` enrollment runs the Codex review; a line on a `claude_code` enrollment runs a Claude review on the Claude ward adapter. `freesided auth adopt -review-harness claude_code` writes `claude-review-default` for `reviewer` instead of the Codex agent: on the review identity's Claude enrollment (the implementation identity's when `-review-auth-identity` names the same identity), on its own offer for `-review-model`, asking `-review-effort`. The daemon composes the review source for the harness its reviewer line names at startup, and each harness takes one `-review-auth-mode`: `subscription` or `api_key` for Codex, `setup_token` for Claude; preflight fails on any other pairing. Moving the line to the other harness therefore needs a restart with the matching mode: until then every review launch refuses, by name, a line on another harness or another vendor's adapter. A Claude review checks out the head it reviews and binds no base; a Codex review binds both.
- **A writer role takes its model and effort from its line.** `freesided auth adopt` writes the writer agents from its six writer flags: for each distinct model and effort that `specifier`, `implementer`, and `remediator` ask, one agent on the Claude ward adapter, named `claude-code-<role>` for the first of those roles that asks it, on a pinned offer of the same name whose `route_model_id` is the exact model id and whose `allowed_efforts` hold the effort; each writer line selects its model and effort on the implementation identity's Claude enrollment. Adoption refuses a writer role with no model or no effort, and the id `claude-code-native-default`, because the writer launch passes `--model` and `--effort` when its line names them and a line that left either out would run whatever the Claude CLI defaults to. To give a writer role another model or effort, edit them in the role's line. A writer line on the model `claude-code-native-default` still launches, with no `--model`, and `daemon/README.md` (Select Agents Through The Lineup) has the steps to move it.
- **An escalated specifier line pairs one enrollment with its escalated model.** Its key is `lineup.role.specifier.escalated.<enrollment-id>`, the enrollment id verbatim (it holds a `/`, which a policy key allows), and its value has the ordinary format, naming that same enrollment with the model and effort the specifier escalates to (`docs/plan.md` §5.13, Specifier Triage). Escalation therefore changes the model and effort and never the credential. The tree is refused when the key's enrollment differs from the value's, when one enrollment has two escalated lines, when the line names the specifier line's own selection, or when its prompt differs from the specifier line's. An escalated line whose enrollment the store lacks, or whose identity is disabled, refuses at admission, not at load.
- **A wardless role may carry one shadow line.** Its key is `lineup.role.<role>.shadow.<shadow-name>`, with the same value format. A second shadow line on one role and a shadow line on a ward role are rejected. A shadow line is never a fallback for a missing primary line. A project lineup that overrides a deployment shadow line reuses its shadow name, because a different name is a second shadow line.

## File Formats

Every file is text that ends with one newline, with no comments and no blank lines. The daemon reads the tree from one exact commit, never the working tree, and refuses the whole revision when any file is outside the layout, does not parse, is larger than 64 KiB, or is not a plain file. `daemon/internal/agenttree` is the reader and the renderer.

- **Agent document** (`agents/<agent-name>`): exactly four lines, in this order. Fields are separated by spaces or tabs, so column alignment is free.

  ```text
  who      enrollment  <enrollment-id>
  through  route       <route-name>
  running  adapter     <adapter-name>
  asking   offer       <offer-name>, effort <effort>
  ```

- **No attended marks** (`agents/<agent-name>.attended`): plan revision 97 removed the attended first run, so an agent is admitted unattended with no mark. A tree that still holds a mark file is refused, naming the file; delete it and commit.
- **Fragments** (`fragments/...`): the fragment's JSON encoding from `daemon/internal/domain` on one line, including its `digest`. Unknown fields and a digest of other content are refused.
- **Lineup** (`lineup`): one `<key> <value>` line for each line, where `<key>` is the part of the policy key after `lineup.role.` (`reviewer`, `briefer.shadow.<shadow-name>`, or `specifier.escalated.<enrollment-id>`) and `<value>` is the selection (`<enrollment-id>/<model-id>/<effort>/<prompt-name>@<prompt-digest>`).
- **Name-to-digest map** (`agents.lock`): one `<kind> <name> <digest>` line for each agent and fragment, sorted by kind and then name. The kinds are `adapter`, `agent`, `offer`, and `route`; an offer's name is `<route-name>/<offer-name>`. The map must equal the digests the content resolves to: a missing entry, an extra entry, or another digest refuses the revision, so an edit to a fragment always shows up in review as a changed digest for every agent that consumes it.

Names: an agent name is lowercase ASCII letters and digits with `-` and `_` inside, at most 246 bytes. A fragment name also allows `.` inside (`gpt-5.6-sol`), at most 255 bytes.
