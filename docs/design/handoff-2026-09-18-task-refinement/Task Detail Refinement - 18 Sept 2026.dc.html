Task detail refinement, 18 Sept 2026 — one pass over everything the Tasks work added this week, drawn against the 18 Sept canvas. Four aims: one visual vocabulary for rows, cards, chips, times, and links; status that reads at a glance again (a bordered mono state chip beside the name, accent only when the operator is needed); progressive disclosure so the current run is the page and history is one click away; and one chronology rule — newest first, current marked — applied to campaigns, runs, milestones, rounds, and events alike. Scope: client presentation only. Every proposal composes components already in FreesideCore — StateChip, KeywordLabel, TechnicalDetailsSection, StageRail, DisclosureGroup, FreesideActionButtonStyle — over the daemon's existing snapshots and timeline. No API, schema, or daemon change is assumed anywhere on this canvas.

Three cuts, one shape. The cut is decided by a predicate, not by the status word: attention when the task has a current open Inbox item bound to it (approval, readiness, adjudication, a failure with a recovery choice) — so "On Hold" is accent while findings await adjudication and ink while the hold is the agent account's queue. Failure is not wax here: wax is for seals and destructive submits; a failed execution that needs a decision is attention like any other decision. Green stays out. The same chip serves the task row, the timeline header, the run card, and the review round.

Progressive disclosure · what the task timeline shows at each layer
0 · Glance
Name, state chip, meta, source, Stop. Answers "what is this and does it need me" without scrolling. The Stop control sits under its own keyword; Technical details is the header's only disclosure.
1 · Current
The current campaign, its current run, open. Attempt title and chip, the review verdict line (round, outcome, open findings) with Inspect reviewer output, and the milestone rail newest first. This is the page; everything below is history.
2 · Detail
Collapsed inside the run card. Round facts (head, base, source, requested and completed, dispositions) under the verdict; Run details (role, attempt reason, parent, recorded hold and code); Technical details. Each closed line carries its summary so nothing is hidden, only folded.
3 · History
Collapsed below the current run. Prior attempts as one-line cards (title, faint chip, last time); older campaigns as one disclosure each (short id, run count, why it ended); Task Events as one disclosure with its count and newest time. Opening any of them never changes the current run's position.
What moves down a layer from today: the review round's eleven fact lines (layer 1 → 2), the campaign keyword's exact id (already in Technical details), Run Activity / Milestones as two stacked keywords (one keyword, Milestones), the run's role, reason, parent, and hold lines (1 → 2), Task Events (1 → 3). What stays at layer 0: the source line and lifecycle, because they are the answer to "which work is this". Nothing is removed; the daemon's facts all remain reachable in two clicks or fewer.

One rule, five places. The daemon already returns campaigns, runs, and events newest first; the review list reverses on the client today (newest round first) and the milestone rail shows its top entry as current. The proposal makes the marker identical everywhere: an 8pt filled ink dot on the newest entry, a 1.5pt hollow dot in milestone-prior on the rest, time trailing in the mono caption. Weight follows the marker — semibold ink for current, regular dim for prior — so the eye reads "now" before it reads a word. Where a list is a rail (milestones) the connector joins the dots; where it is a set of cards (campaigns, attempts) the dot sits in the closed line. Nothing is ever re-sorted by timestamp on the client; the order is the daemon's, and "current" means position 0, never "most recent clock".

Ledger · changes by component · open items
Changes
  • TaskRowView — status line becomes a StateChip beside TaskNameLabel; round and hold join; guidance renders in the link recipe; padding 14; "last active" prefix dropped from the meta line.
  • TaskDisplay.Position — the chip's cut is derived client-side from what the row already computes: attention when the existing guidance resolves to a current Inbox item bound to the task (the same attentionItems the list receives today), faint when the position is historical, ink otherwise. No new field from the daemon.
  • TasksListView — the caption under the scope control is removed.
  • TaskTimelineView — header meta collapses to one mono line; run card gains chip, Run details disclosure; non-current runs render as one-line cards; non-current campaigns render as one disclosure row; Task Events becomes a disclosure with count and newest time.
  • RunReviewSection — round card becomes a verdict row (marker, round, outcome chip, time) over a Round facts disclosure; prior rounds fold to one hollow line; title keyword, not serif; time format joins recipe 04.
  • TaskStopView — Stop task… takes the wax outline (T1 on the 18 Sept canvas); the rest of T1 stands.
  • StageRail milestone marker — current fill moves from accent to ink; prior stays milestone-prior. Accent is now attention-only across the task surfaces.
Stays

The API and every daemon contract; the status vocabulary and its precedence (#1374); the per-phase sentence; the combined accessibility element and its string order; ids in Technical details (#1379); the run timeline's own rail and hold card; Inbox rows. Every new element on this canvas is an existing component in a new arrangement — the only additions are SwiftUI disclosures and layout.

Open
  • Should the run card's chip repeat the task chip when the current run is the task's position? Drawn as repeated; dropping it leaves the attempt title bare.
  • Disclosure state persistence: per task, per device, or session only? Decision Detail's inspector persists per section; the same rule is proposed.
  • "Findings · 2 open" reads the existing RunReviewRound.dispositions; when the daemon omits it the chip reads "Findings · 2". Campaign and event summaries ("2 attempts · since Sep 11", "6 recorded · newest …") are counted from the timeline already on the client.
  • Differentiate Without Color: the attention cut already differs by border tone; a leading ◆ glyph is the fallback if contrast testing asks for it.
