What we should build from the review — and what we should not

The review is largely right and unusually specific. Every one of its twenty-seven findings is worth acting on; nine need their solution changed, one is right but premature, and four of its proposed remedies should be refused because they trade Freeside's identity or its low-vision users for implementation convenience. Below: a verdict on every finding, then a worked example of each accepted proposal — mocked where color, type, and contrast carry the decision, wireframed where the proposal is structural.

Four remedies to refuse
P0-1 Solution A — cap Dynamic Type inside cards

The review calls this the wrong product decision and it is right. Capping trades a layout bug for a permanent exclusion of the users who chose the larger text. Reflow instead — 1a.

P0-2 Solution A — swap the palette for system colors

This discards the thing the same review calls a product advantage in order to inherit four variants we can author in a day. Author them — 1b.

System red for destructive controls

Wax is Freeside's failure and revocation color everywhere else; a red Stop beside a wax "failed" chip teaches two reds. Keep wax in content, and take the native destructive role only on system-owned surfaces — confirmations, menus — where the system paints its own red. Fix wax's dusk contrast instead — 1b.

Sticky action footer on macOS

A bar floating over a desktop detail pane is a web habit. The Mac has the width to keep the primary action in view without one: put it in the card's trailing action area — 1g. Keep the sticky safe-area inset on iPhone only.

Worked proposals

Twelve examples covering every accepted finding. Fidelity is a decision, not a default: contrast, badge weight, and recommendation prominence are argued as mocks because their entire content is color and type. Navigation and pane structure are argued as wireframes, because a mock there only invites an argument about paint.

What changed
No repeated title. The navigation bar names the type; the card opens on the question. That alone returns a full line of text at AX5 (P2-1).
Badges become a text line. Priority and waiting time as a two-line mono block: no chip geometry to break, no per-character wrapping, and open is gone in the Open scope (P2-2).

Build rules
  • Switch composition on the size category, not on width: at .accessibilityMedium and above, header, facts, and action rows go vertical.
  • Chips render single-line and non-compressible, or they render as text. Never a fixed-width chip with wrapping content.
  • Buttons grow vertically; labels wrap to two lines rather than truncating.
  • Disclosure state is composition-dependent: expanded at standard sizes, collapsed at accessibility sizes.
  • VoiceOver order matches the visual order exactly: type, urgency, ask, recommendation, action, facts, evidence, details.
  • Screenshot regression at xSmall, Large, xxxLarge, AX1, AX3, AX5 for inbox, every card type, run list, run timeline, and pairing.

Mock · tokens · both grounds P0-2Client only

Build rules

  • Washes carry no threshold because they carry no meaning alone — every wash pairs with a text token and a glyph.
  • Differentiate Without Color is a separate pass from contrast; see 1e for selection and 1h for status glyphs.

Build rules
  • Code field uses one-time-code semantics and the ASCII-uppercase keyboard the daemon's alphabet actually needs; grouping is display-only, never validation.
  • Paste accepts the code with or without its separator, and trims what the terminal put on the clipboard.
  • Device name prefills from the system device name and stays editable; the helper states both places the name appears.
  • Pairing never shows a credential, a token, or a key — only the host, the code, and the name.
  • Watch chips are single-line and wrap; the hold line is the only line permitted to use emphasis, because it is the reason the run is on screen.

What is client-only, and what needs the daemon first

Most of what is proposed above is recomposition inside the app: it changes order, weight, and wording of data the client already holds, so it can start now and needs no contract change. The rest is not a UI problem wearing a UI mask — a recommendation the client infers, a fact the client parses out of prose, or a button whose transaction does not exist would each be a worse product than the current honest mess. Those belong in the Wave 7 attention-contract unit, ahead of the client work that consumes them, and they are what makes "approvals are decidable from the phone" testable rather than approximated.

Work item A · client recomposition no contract change
Ships against today's API, in any wave
Colour variants and Increased Contrast (1b); the accessibility composition (1a); tabs and independent stacks (1f); inspector, two-column card, empty-pane summary (1g); badge, time, count, and selection rules (1e); durable confirmation and deliberate advance (1j); refresh, last-updated, keyboard, menus, menu-bar route (1k); two-line run rows (1l); the card shell's order, measure, and help placement (1c); action ranking, overflow, confirmation copy, and destructive roles (1d).
This is the majority of the review by finding count, and all three of its release blockers except the facts behind them.
Work item B · Wave 7, before the 1B exit contract first
Phase 1 attention presentation & action contract
Five things, in this order, each landing before the client work that draws it:
1 · Recommendation authority. recommended_action, recommendation_reason, recommendation_source (deterministic policy · validated agent judgment · human policy), and confidence where it exists. Feeds 1c, 1h.
2 · Typed minimum facts per card type. The §9 table as daemon projections: readiness gates and change summary, failure class and failing step, both dispute positions, per-round finding trend, blocked-since and clearing condition. Feeds 1h.
3 · Transactions behind the actions we display. Whatever survives the decision in the callout below.
4 · Evidence metadata. Validated media type, byte size, producer, creation time, source run or claim, availability status. Feeds 1i.
5 · Operational identity. Pairing-code expiry, host display identity, local versus relayed, granted scope. Feeds 1l. Also: human project and work-unit names for the row's third line (1e).
Work item C · Wave 7 instrumentation
The comprehension telemetry §8 and §9 already prescribe — open-to-decision latency, drill-down by type and device, non-recommended choice rate, time on unavailable actions. Typed events, small and privacy-conscious; no clickstream. Landed in Wave 7, read in Wave 8, because these are the numbers that say whether any of this worked.
Work item D · Wave 8 evaluation
Wave 8 consumes the contract and answers four questions per card type: can it be decided from iOS, does every shown action execute, can the operator identify the recommended path, can they see enough to reject it. A missing core fact found here is an exit-blocking 1B defect, not Wave 8 scope. The review's own verification criteria make a serviceable exit checklist.
Work item E · Phase 2 and later
Search, with its query API, indexing, pagination and authorization, is new scope and belongs here — as does OCR and derived previews, richer or risk-classified card types, and grouping metadata. Live and mid-turn conversation stays Phase 3. Note that 1k only reserves ⌘F; nothing in the client work depends on this.
The one decision that cannot be made in the client
Hiding unsupported actions (1d) removes the noise, and I would ship it either way — but it does not settle P1-2, and it must not be allowed to look like it did. An action that is hidden is still an action the daemon requested and nobody can take. Two honest resolutions, and only two:
Implement the transactions in Wave 7
discuss, continue_under_policy, convert_to_policy, adjudicate, request_changes, answer_and_retry, answer_without_retry, return_to_agent, retry_with_capabilities, choose_alternate_profile — each with payload, validation, idempotency, transition, outcome, sync, and retry semantics. Asynchronous discussion counts; live streaming does not.
Or remove those workflows from the 1B exit claim
Diminishing-returns review sits inside the 1B chain, so if continue_under_policy and convert_to_policy do not execute, that card is not decidable from the phone and the exit criterion should say so. The capability-mismatch state in 1d is the honest presentation of that choice — not a substitute for making it.
